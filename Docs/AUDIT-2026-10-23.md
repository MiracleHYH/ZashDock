# ZashDock 完整实现审计

审计日期：2026-10-23（Asia/Shanghai）。基线提交：`3c58f45917c2a01d1c9526b6e03a0021da258f97`。

**结论：当前是核心流程已实现、能够运行的开发预览版，尚不足以作为稳定版交付。** 最大差距是网页文档生命周期中的数据一致性、官方网页文件交互兼容，以及异常后的原生恢复闭环。继续开发应先解决这些问题，再补齐完整数据迁移和真实签名更新验收。

本轮检查全部生产 Swift 源码、Core、Xcode/SPM 配置、原生 UI、测试、发布脚本与工作流；核对 Apple 官方 API、已安装 SDK 和 WebKit 官方实现，并通过独立探针验证反例。生产实现未修改；未访问用户生产配置或 Keychain，未修改代理、远端 Kernel、仓库设置或发布状态。探针使用独立临时目录、虚构 Remote、固定测试密钥和非持久化 WebKit。

P1 表示下一阶段应先修复的数据安全或核心功能问题；P2 表示稳定版前应补齐的可靠性和交互问题；产品缺口与尚未完成的验收单独列出。本轮未发现已证实的 P0 安全漏洞，这不构成安全保证。

F01 的根因有两部分：用户脚本在每个 document 开始时把 LocalStorage 清空并恢复旧 seed，而原生消息序号属于整个桥接实例，未区分 document。新文档从 0 开始，消息一度被旧序号忽略；序号追平后，回退后的状态又会成为权威快照。原生菜单的重新载入会创建新的桥接，现有测试对此通过，不能覆盖网页自己的 `location.reload()`。官方网页的设置导入、部分设置变更和页面重载确实使用这种路径。

F01 探针使用 `setup/api-list` 与 `setup/active-uuid`：启动 seed 有一个 Remote，运行中添加第二个并选中；同一 WebPage 再次加载同一 Origin 后，页面只剩一个且选中项回退。继续编辑 20 次并 flush 后，Vault 也只剩一个。修复需要设计 document 身份、序号和快照的生命周期，并阻止旧文档尾消息覆盖新文档；单独放宽序号检查或只在 LocalStorage 为空时恢复都不足以解决事务语义。

F02 中，未指定 dialogPresenter 不会自动获得原生对话框。WebKit 使用空的默认 presenter；文件选择、confirm、prompt 默认取消，alert 默认无声返回。需要用 macOS 26 可用的 `WebPage.DialogPresenting` 接入原生呈现，并验证来源、主框架、文件类型、取消和用户选择的文件作用域。ZashDock 原生 ZIP 导入使用 SwiftUI fileImporter，不受这项缺陷影响。

F03 的源码缺口是确定的，但本轮没有执行“官方界面点击导出并成功保存文件”的验收，不能把允许 `.download` 当作已支持下载。后续应实现受限的数据导出与用户选择保存位置的原生流程；网页不能自行指定任意原生路径。必须实际比较导出文件内容并覆盖取消、重复文件名、非受信来源和超限数据。

F04/F06 的修复要保留普通配置、版本资源、加密数据三者的边界。配置损坏可以保全原文件后让用户恢复备份或重置端口/窗口选项；不能连带清除 Remote。密钥失败应区分暂时不可读与永久丢失，提供重试、备份选择和明确的数据恢复决定，继续禁止自动生成新密钥覆盖旧密文。保留旧数据的现有策略是正确的，缺的是可操作的恢复界面。

F07 应让页面运行状态进入原生状态机。页面失效后应保全最近有效快照并提供重载；退出失败应说明未保存的状态，并允许重试或由用户明确选择使用已保存状态退出。本轮将“缺少恢复闭环”与主动保护未落盘数据的策略区分开来。

**原始范围尚未补齐的能力**

| 能力 | 当前范围 | 需要补充 |
| --- | --- | --- |
| Origin 数据迁移 | 完整 LocalStorage；IndexedDB 不跨端口 | 背景图和连接历史等 IndexedDB 数据应纳入有版本、配额、加密和恢复顺序的快照；若阶段性仍不支持，应在更换端口前原生明确提示 |
| 网页文件交互 | 原生 ZIP 导入可用；网页文件选择和 Blob 保存未完成 | 实际官方网页的配置导入/导出、背景图片、图标导入，以及取消和权限边界 |
| 发布签名与应用更新 | Sparkle 配置、空 Feed、检查无更新可用 | 真实签名旧版 → 新版的检查、下载、安装、退出前保存、重启、两个 Remote 保留；坏签名及中断恢复 |
| 配置恢复 | 坏主快照可回退认证备份，完全失败时保留原文件 | 原生恢复页、可重试的启动状态、保全文件、明确备份导入/重置决定 |
| 原生产品外观 | 标准窗口、Toolbar、Settings、菜单 | App 图标；String Catalog 与语言维护；原生错误分类和清晰的操作反馈 |
| 辅助功能 | 使用部分系统控件 | VoiceOver、键盘全流程、深浅色、增强对比度、减少动态效果和较大字号布局的实测记录 |

IndexedDB 完整迁移需要明确数据类型和异步恢复顺序，不能把 LocalStorage 的 JSON 字符串复制直接视为完整 Origin 迁移。当前快照协议、资源限额和加密存储需要为二进制与数据库 schema 设计扩展，并保持恢复完成后才让官方网页读取。

稳定版前应新增以下测试，按失败影响排序：

1. 两个 Remote 经网页 `location.reload`、完整同源导航、后续编辑、退出与重启的一致性；同时检查页面和 Vault。
2. 官方网页文件导入、confirm/prompt/alert、Blob 导出真实文件；覆盖取消和桥接来源边界。
3. 配置 invalid JSON/错误类型/缺失字段、快照主备损坏、密钥暂时不可用和修复后的原版本/Remote 保留。
4. 下载进行中取消、断网、API 超时/限流、错误长度/摘要、非法重定向；通过可注入网络层或受控 fixture 验证。
5. 磁盘满、写权限丢失、rename/fsync 失败；在复制、解压、目录移动、候选验证、指针提交、清理各阶段终止进程后的重启恢复。
6. 两个不同真实官方 Zashboard 版本的升级和回滚；真实签名 ZashDock 自更新和安装中断恢复。
7. 独立 macOS 26 环境，以及当前系统的签名沙盒运行；不能以 SDK availability 或 macOS 27 通过替代最低系统运行。
8. VoiceOver/键盘/UI 自动化、睡眠唤醒/网络切换/持续 WS、启动与空闲资源基线。

**发布与维护补齐项**

正式发布前仍需配置 Developer ID 与 Apple 公证凭据，并实际演练 Archive/export、notarytool、staple 和在线更新。脚本语法、Actionlint、空 Feed 签名通过不能替代这些步骤。需要单独保存每个发行的 dSYM、源提交、Xcode/SDK 版本和公开构建元数据，避免上传含临时密钥的整个目录。

本轮只读查询仓库时，尚无 GitHub Environment、main 未受保护、rulesets 为空；Secret scanning 与 push protection 已开启。发布治理应采用适合个人开发的策略：限定发布来源、验证 CI、让发行 Secret 仅在必要步骤可用。reviewer 可按协作人数选择，不能给单人维护设置无法完成的自审门槛。若增加分支规则，须同时设计 release.sh 的 Feed 提交流程；当前直接 fast-forward 推送 main，不能假定启用保护后仍可原样运行。

应演练“Release 已公开但 Feed 推送失败”的恢复，并验证旧 Feed 仍可用、恢复时不丢已有条目。还需定期跟踪 WebKit 与 Zashboard 的存储 schema/文件交互变化，以及 Sparkle 更新；当前锁定依赖版本是正确基础。
